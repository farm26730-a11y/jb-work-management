# JB 업무 원본 연동 계약 v1

개발용 미리보기는 합성 입력으로 이 모듈을 호출한다. 기존 업무앱 실행 경로와는 분리되어 있다. 배포 시 별도 서버 조회 계층이
승인된 보고 범위의 업무와 이력을 읽고 `adaptDailyTaskSource()`를 호출한다.
어댑터는 원본 형태와 조회 완전성을 확인한 뒤 기존 `summarizeDailyTaskTime()`에
전달한다. 이 단계의 구현은 네트워크 연결이 없는 순수 함수다.

## 호출 계약

- 입력은 서울 기준 `date`, `cutoffTime`, 원본 `employeeId`(UUID), `source`다.
- 성공 입력의 `source`는 `status: 'ok'`, `authorization: 'verified'`,
  `contract: 'jb-task-source-v1'`,
  `scope: 'all_tasks_created_through_cutoff_with_history'`를 포함한다.
  `snapshotId`는 읽기 스냅샷의 식별자이고, `cutoff`와 `asOf`는 UTC다.
  `asOf`는 마감 이상이어야 한다. 마감 이후 업무 상태는 마감 시점 상태로
  비교하지 않는다. 이 메타데이터는 인증된 서버 조회 계층에서만 생성한다.
- `schema`는 테이블별 필수 열의 DB 타입과 null 허용 여부를 포함한다.
  예를 들어 `uuid!`는 필수, `uuid?`는 nullable이다. 모듈의 `columns`에
  전체 목록이 있다. `taskStatuses`는 현재 업무 상태 CHECK의 허용값 목록이다.
  UUID는 표준 소문자 표기, 시각은 UTC `YYYY-MM-DDTHH:mm:ss.ffffffZ`로
  변환한다. `changed_by`, `previous_status`, `assignee_id`의 SQL NULL은
  명시적으로 전달한다. 업무명·설명·직원명은 계약에 포함하지 않는다.
- `tasks`와 `history`는 각각 `{count, pages}`다. 각 페이지는
  `{status:'ok', snapshotId, after, done, rows}`다. 첫 페이지의 `after`는
  null이고, 다음 페이지는 직전 마지막 행의 키를 사용한다.
  업무는 id 순, 이력은 (changed_at, id) 순이다. 이력 커서는 UTC 시각과
  소문자 UUID를 슬래시로 연결한다. 마지막 페이지만 `done: true`다.
  조회가 정상적으로 0건이면 count 0과 빈 마지막 페이지를 전달한다.
- 선택 입력 `assignmentLedger`는 같은 `snapshotId`와 `periods`를
  포함한다. 각 기간은 `{taskId, employeeId, from, to}`이며 UTC 반개구간
  [from, to)이다. null 종료는 열린 배정이다. 이 입력은 권한이 확인된
  서버가 독립 배정 원장을 검증한 뒤에만 제공한다. 현재 업무 행의 임의
  검증 플래그는 무시한다. 합성 화면은 별도 예제 원장을 사용한다.
- 결과 `ready`는 입력 범위 검증을 통과했다는 뜻이다. 업무 원본 자체가
  0건이면 `empty`다. 권한 부족은 `forbidden`, 조회 실패는 `error`,
  페이지·범위 오류는 `incomplete`, 필수 열·상태 계약 불일치는
  `incompatible`이며 이 경우 `report`는 null이다.

## 서버 조회 설계

1. 보고 조회 역할과 대상 직원 UUID를 먼저 확인한다. 권한 확인과 SQL 조회는
   서버에서 수행한다. RLS로 예상 범위가 숨겨진 경우를 빈 성공으로 처리하지
   않는다. 앱이나 공개 브라우저에는 조회 권한이나 비밀을 배포하지 않는다.
2. 하나의 읽기 전용 반복 읽기 스냅샷에서 마감까지 생성된 업무와 그 업무의
   마감 이하 이력을 같은 조건으로 각각 COUNT하고, 같은 범위를 키셋 페이지로
   읽는다. count는 페이지를 더해 만들지 않는다. 스냅샷 식별자는 연결 계층이
   발급한다. 독립 HTTP 요청에 같은 문자열만 부여하는 방식으로는 스냅샷의
   일관성을 보장할 수 없다. 마지막 페이지와 건수·커서·ID를 대조한다.
3. 생성 시점부터 이력을 넘겨 자정 이전 상태를 복원한다. 조회 검증에 실패하면
   부분 집계를 발행하지 않는다. 같은 시각의 ID 순서는 조회 경계에만 쓴다.
   이력 내 상태 모순은 엔진이 구간 미확인으로 표시한다. 원본 DB에 애초에
   기록되지 않은 전환까지 페이지 검사로 검출할 수는 없다.
4. 현재 담당자는 후보만 식별한다. 배정 확인 테이블은 일부 배정을 갱신하거나
   삭제하므로 기간별 배정 근거로 사용할 수 없다. 기간 근거가 없으면 현재 담당 업무를
   `unverifiedAssignment`로 반환한다. 해당 직원의 후보가 0건이어도
   다른 사람에게 재배정된 과거 업무의 부재를 증명하지 못한다. 실행자
   `changed_by`는 담당자를 대신하지 않는다. 독립 배정 원장에서
   업무 생성 또는 서울 자정 중 늦은 시점부터 마감 정각까지 동일 직원의
   연속 배정을 확인하면 `reportAssigneeId`로 귀속한다. 실제 현재 담당자는
   `currentAssigneeId`에 별도로 유지한다. 보고 구간 내 재배정이나 공백은
   미확인이며, 구조적으로 잘못된 원장·다른 스냅샷·겹친 기간은 오류를 반환한다.
   어댑터의 검증은 입력 원장의 실제 권한·출처에 대한 서버 검증을 대체하지 않는다.
5. 배포 전 카탈로그 열 정의와 업무 상태 CHECK를 계약과 비교하고, 각 조회
   배치의 행도 검사한다. 열 추가는 허용한다. 필수 열의 이름·타입·null 규칙,
   ID 체계, 상태 의미가 바뀌면 새 원본 매핑과 합성 호환 테스트를 추가한다.
   외래 키 관계, RLS 범위, 상태 이력 트리거 의미는 배포 전 별도로 대조한다.

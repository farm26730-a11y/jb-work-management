## 3. 운영 역할 및 사용 규칙 — 기능 보존 기준
1. 역할 **대표(owner)**, **관리자/부서장(manager)**, **직원(staff)**. 관리자는 소속 직원 근태 승인; 직원이 자기 신청을 승인하지 못하게 한다.
2. **관리자 자신의 휴무는 자동 승인** 동작 유지. 단 연차 잔액 확인 우회 가능성이 있어 보안·정합성 보완 대기.
3. 대표 홈에는 일반 직원 휴무 승인 요청을 불필요하게 노출하지 않고, 관리자 홈 **오늘 업무 현황 → 확인 요청**에서 해당 직원 휴무 신청을 확인·승인·알림.
4. 직원의 **대표님 직접 보고**는 대표 확인 요청으로, 업무 지시/댓글 확인은 해당 담당자에게 필요한 홈 알림으로 처리.
5. 업무 진행 상태 `예정` / `진행중` / `보류` / `완료`; 시간 누적, 업무 댓글, 업무 사진, 완료 보관함/상세 조회, 식사, 출근 배치, 공지, 푸시 등 기존 기능 보호.
6. **활성 직원 누구나 다른 직원·다른 부서·관리자가 직접 등록한 업무에도 댓글 작성과 해당 댓글의 사진 첨부 가능**해야 한다. 현재 운영에서 **사진 업로드만 막히는 오류가 있어 개발 채팅방 수정 중**이다. 댓글 작성 권한과 업무 사진 권한을 혼동하지 말 것.
7. 다른 직원의 댓글을 임의 수정하거나 사진을 끼워 넣는 행동은 허용하지 않는다. 사진은 댓글 아래에 표시하고, 업무+댓글 사진 총 5장 제한 유지.
8. 직원용 화면에 개발/시험/서버 설정/SQL/RPC/버전 이력 안내를 넣지 않는다. 꼭 필요한 설명과 사고 예방 경고만 짧게 작성한다.
9. 연차는 입사일 기반 발생일 자동 계산 및 수동 차감(0.5일 단위)을 제공하되, 실제 개근·80% 출근율/장기휴가·이월 기준 부족으로 **잠정값을 법정 확정 잔액으로 단정하지 않는다**.
10. 운영 기록 전체 초기화, 데이터 삭제, 본인 연차 사용 이력·장부의 수동 조정은 실제 자료 손상 가능성 때문에 충분한 사전 검증 및 사용자 승인 없이는 실행하지 않는다.

## 4. 운영에 미반영된 개발 수정 — 혼동 금지
### `JB-261115-01` 댓글 사진 권한
- 운영 증상: 관리자가 자기 업무로 등록한 일에 직원이 사진을 첨부한 댓글을 만들려면 업로드 실패 가능.
- 발견 원인: 운영 Storage/사진 DB INSERT가 `jb_photo_can_upload`로 **업무 담당자·같은 부서 관리자·대표**만 허용. **댓글 작성 권한**보다 좁음.
- 개발 대응: `JB-DEV`에서 본인이 작성한 댓글인지와 해당 업무 소속인지 검증하는 `jb_comment_photo_can_upload_v13` + Storage 및 사진 기록 RLS. 일반 업무 사진의 권한은 별도로 유지.
- 보고 댓글도 서버가 반환한 **정확한 댓글 ID**를 사용하도록 신규 래퍼 RPC 구현. 댓글 사진이 실패하면 동일 댓글에서 재첨부 가능.
- 시험: 개발 DB에서 **다른 부서 직원→관리자의 본인 업무 댓글 INSERT→사진 DB 기록 RLS INSERT 성공**(임시 데이터 롤백), JS 문법 및 사진 댓글 모의시험 통과.
- **개발 Netlify의 실제 Storage 파일 전송/갤럭시 실계정 시험은 아직 미실시.**
- SQL 변경 파일: `development/2026-11-15/JB_V1_3_댓글사진_작성자권한_추가.sql`, `development/2026-11-15/JB_V1_3_보고댓글_정확한_댓글ID_반환.sql`.
- **운영 Supabase에는 위 SQL을 설치하지 않았으며**, 운영 main에도 신규 기능 코드 미반영. 일부 기능만 따로 옮기면 댓글/사진 연결이 깨질 수 있으므로 반드시 짝을 맞춰 검토.

### `JB-261115-02` 직원용 앱 불필요 안내 삭제
- 개발 브랜치에서 개발·시험·서버기술 설명 및 과도한 사용자 안내 총 42곳 정리. 핵심 도움말/삭제·연차 경고 유지.
- **운영 main에는 아직 미반영**.

### `JB-261115-03` 사진만 댓글 등록
- 개발본은 댓글 글자 없이 사진만 선택해도 `사진 첨부` 본문으로 등록. 이전 운영 코드의 `required` 본문 조건으로 사진만 제출이 막힐 수 있음.
- 개발에서 직원·관리자·대표 모의시험 통과. **운영 main에는 아직 미반영**.

### 다른 개선 대기
- 관리자 본인 휴무 자동승인 시 연차 잔액 검사 우회 가능.

8. 장애가 발생하면 이전 정상 배포/백업 기준으로 복구하되 되돌리기 방법과 영향받은 실제 자료를 먼저 검토한다.
9. 공통 대장에 **작업 ID, 운영 main commit, 운영 Supabase migration, Netlify URL·Published 시각·SHA, 실기기 결과, 남은 위험, 복구 계획**을 기록한다.

## 7. 운영 채팅방과 개발 채팅방의 통신 규칙
- **운영 → 개발:** 재현된 운영 오류를 공통 대장에 `접수`로 등록. 담당 코드/SQL, 영향 받는 기능 및 사용자 증상을 기재한 후 개발 채팅방에서 별도 수정·시험.
- **개발 → 운영:** 개발 채팅방이 공통 대장에 `릴리스 후보`, 커밋·마이그레이션·권한/보안 영향·검증 결과를 작성. 운영 채팅방은 이 자료를 읽고 `main`으로 무엇을 배포할지 독립 검토.
- **운영 배포 승인:** 채팅방 간 공유 기록만으로 승인된 것은 아니며 **사용자의 명확한 운영 배포 지시**가 별도로 필요.
- **배포 후:** 운영 채팅이 대장 상태를 `운영 게시 확인`으로 갱신하고 결과를 다시 개발 채팅이 조회. 별도 채팅 메시지 자동 동기화는 없고 GitHub 기록을 통해 수동 공유한다.
- 공통 자료는 **`development-test/handover/`에만 보관**하며, 문서를 갱신하는 행위를 운영 `main` 수정과 혼동하지 않는다.

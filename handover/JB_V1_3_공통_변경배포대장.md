## 2026-11-16 반복 업무 양식 개인별 분리 확인 — `JB-261116-01`
- 요청: 직원들의 반복 업무 양식이 서로 공유된 것처럼 보여, 각 직원이 **자신만의 반복 업무 양식**을 갖고 있는지 확인.
- 검증 대상: 운영 `main`, 개발 `development-test`, 운영 Supabase `bnonnvgtbukztfhaxgrr`, JB-DEV `apkrhhdmjxbvwtdktfaq`.
- **두 브랜치의 실제 코드 동일:** `loadRepeatTemplates()`는 `jb_task_templates`에서 `.eq('owner_id',profile.id)`만 조회. `saveRepeatTemplate()`는 `owner_id:profile.id`로 INSERT, `deleteRepeatTemplate()`는 `id` + `owner_id=profile.id`로 삭제. 로그인 프로필 교체 시 템플릿 배열 초기화 후 재조회.
- **운영/DEV 양쪽 SQL RLS:** 활성 직원 검사(RESTRICTIVE) + SELECT/INSERT/DELETE 모두 `jb_task_templates.owner_id = 로그인 인증 사용자에 연결된 jb_employees.id` 강제. 타 계정 양식 공유 권한 없음.
- 운영 DB 읽기 전용 스냅샷: 양식 73개 / 작성 직원 7명(직원 4명 68개, 관리자 2명 4개, 대표 1명 1개). 소유자 미연결·비활성·auth 사용자 중복 0건. 서로 다른 소유자에게 동일 제목의 양식이 저장된 제목 2종은 확인됐지만, 제목 중복이 공유를 뜻하지는 않음.
- **JB-DEV 실제 RLS 트랜잭션 시험 통과:** 임시 직원 A와 B(서로 다른 인증 UID) 생성, A 양식 INSERT/SELECT 성공, B의 A 양식 SELECT 0건, B의 A 양식 DELETE 0건, B가 A 소유로 INSERT하려는 요청 권한 거부, B 자신의 양식 INSERT/SELECT 성공. 마지막 `ROLLBACK`으로 테스트 자료 모두 폐기. 운영 DB 쓰기·GitHub 앱 코드 변경 없음.
- **확인된 결론:** 서버가 서로 다른 정상 계정에 개인 양식을 공유하도록 설정되어 있지는 않음. **사용자가 실제로 본 화면에서 두 계정의 양식이 함께 뜨는지는 아직 재현/검증하지 못함**. 배포된 실사용 Netlify 프로젝트가 `main` 최신 코드인지, 직원들이 같은 로그인 계정을 사용 중인지, 홈의 전 직원 업무 목록과 '반복 업무 간편 등록' 양식 목록을 혼동한 것인지 별도 확인 필요. 실제 화면/로그인 프로필/배포 상태를 확인해야 확정 진단 가능.
- 상태: **코드·RLS 확인 완료 / 실사용 증상 미재현**. 변경 작업 보류; 화면 증빙 후 원인 규명. 운영 배포 불필요.

## 5. 개발 → 운영 변경 전달서 필수 항목
새 작업을 넘길 때 다음 항목을 **작업 ID 기준으로** 이 파일에 추가한다.

```text
[공통 변경 전달]
작업 ID:
요청자/기록일:
변경 목표와 사용자 증상:
개발 브랜치 및 기준 커밋:
변경 파일 (HTML/함수/SQL 등):
개발 Supabase migration 이름:
운영 DB 변경 필요 여부 및 영향:
권한·보안 영향:
검증한 시험 / 미검증 시험:
기존 기능 회귀 위험 및 롤백:
운영 반영 요청 및 사용자 승인 상태:
운영 main 커밋 (운영 반영 후):
운영 Netlify 사이트·Published 커밋 및 시간:
운영 실계정/갤럭시 결과:
최종 상태:
```

- 개발 채팅은 `릴리스 후보`까지 작업하고 `main`/운영 DB를 **승인 없이 변경하지 않는다**.
- 운영 채팅은 제출된 작업 ID·변경 파일·SQL·시험 근거를 독립 검토하고 **사용자의 명시적 운영 반영 요청**이 있을 때만 운영 적용한다.
- 순서: 운영 백업/롤백 준비 → 운영 사이트/브랜치 확인 → 필요한 SQL의 안전성·권한 재검토 → 필요한 코드만 `main` 반영 → Netlify Published 확인 → 대표/관리자/직원 실계정 및 갤럭시 시험 → 대장에 결과 기록.
- 기존 GitHub `main`이 개발과 갈라져 있으므로 전체 `index.html`, `netlify.toml`, `public-config.mjs`를 검토 없이 통째로 복사하지 않는다. 특히 개발 전용 JB-DEV URL 가드를 운영에 넣으면 운영 로그인이 차단될 수 있다.
- 운영 버그를 긴급 수정한 경우 운영 채팅이 `main` 패치 후 대장에 기록하고, 개발 채팅이 검토하여 `development-test`에도 같은 수정 사항을 역반영한다.

## 6. 보안·사용자 경험 공통 원칙
- 두 프로젝트의 `SUPABASE_URL` 및 공개키/비밀키를 절대 혼용하지 않는다. `service_role`, 새 Secret Key, VAPID 개인키를 문서·채팅·GitHub·HTML에 적지 않는다.
- 사용자 앱 화면에는 개발/시험/디버그 메시지, SQL·RPC·스키마·서버 내부 설명을 쓰지 않는다. 꼭 필요한 사용법과 실제 위험 경고만 간단히 표시한다.
- 활성 직원은 **다른 부서 직원 및 관리자가 자기 업무로 등록한 업무라도 댓글 작성과 자기 댓글 사진 등록 가능**. 단 타인 댓글/사진 임의 수정은 불허.
- 업무 사진+댓글 사진의 총 5장 제한, 이미지 압축, 대표/관리자/직원 권한, 홈 확인 요청, 직원 휴무 승인, 관리자 자신의 휴무 자동승인 등 기존 기능을 함부로 깨지 않는다.
- 연차 자동 계산값은 개근·출근율 등 자료 미확보 시 **잠정**이며 법정 확정 잔액으로 안내하지 않는다.
- 초기화/사용자 삭제/연차 차감/승인/대량 배포는 데이터 손실·권한 위험을 검토하고 명확한 승인 없이는 실제 운영 자료를 변경하지 않는다.

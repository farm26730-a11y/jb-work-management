## 2. 앱 코드 및 역할 규칙
- 제품: **JB 업무관리 V1.3**. 정식 새 버전 승인 전까지 화면 표기는 V1.3 유지.
- 전체 실행 앱: `JB_97EBB4B4EBAC_V1_3_A1EAB89DECA0A7EBB7A6ED8C9DEDB88BEC9CB2ECA4B9EDA882EC80/index.html`.
- 같은 폴더의 `sw.js`, `manifest.webmanifest`, `netlify.toml`, `netlify/functions/` 포함. 기존 정상 기능을 보존하고 **파일 전체와 관련 함수의 영향까지 검토**할 것.
- 역할: **owner(대표)** / **manager(부서장)** / **staff(직원)**. 대표 전체 관리, 부서장은 소속 직원 관리, 직원은 본인 허용 업무. 기존 본인 업무 상태·시간 기록과 보고/근태 승인 규칙 유지.
- 직원 휴무 신청은 부서장 홈의 확인 요청에서 승인·알림; 대표 홈에 일반 직원 휴무 승인 대기 불필요 노출 금지. 관리자 **자신의 휴무 신청은 자동 승인**(이 동작의 연차 잔액 우회 위험은 별도 개선 대상).
- 모든 활성 직원은 **다른 직원/타 부서/관리자가 스스로 등록한 업무에도 댓글을 작성하고 그 본인 댓글에 사진을 첨부**할 수 있어야 한다. 댓글/댓글 사진에 담당자·지시자·동일 부서 제한 추가 금지.
- 타인의 댓글 수정·삭제·사진 임의 추가는 기존 권한으로 보호한다. 사진은 댓글 바로 아래 표시, 업무 기본 사진과 댓글 사진 합계 최대 5장. 원본 JPG/PNG/WEBP 25MB 이하, 업로드 전 자동 압축/저장소 5MB 이내.
- 직원이 **사진만 첨부하는 댓글**도 등록 가능해야 함. 댓글 내용이 없고 사진이 있으면 개발 코드가 `사진 첨부` 문구로 댓글을 만들고 해당 댓글 ID에 사진을 연결한다.
- 개발 과정·시험·RPC·스키마·DB·서버 관련 설명은 **직원용 앱 화면에 넣지 않는다**. 오직 실제 사용법과 필요한 안전 경고(연차 잠정값, 삭제 경고, 오류 처리 등)만 간단히 표시. 상세 기술 내역은 인수인계/개발 기록에만 작성.

## 4. 개발본에 이미 반영됐으나 실사용 시험이 남은 기능
### 4.1 관리자 자신의 업무에 다른 직원이 댓글·사진 등록
**개발 코드 및 DB 정책 반영 완료 / 운영 미반영.**
- 운영 사진 업로드 검사 `jb_photo_can_upload`가 담당자·같은 부서 관리자·대표 중심이어서, **타인 업무에 작성한 댓글**의 사진 저장을 막을 수 있었음.
- DEV 신규 SQL: `development/2026-11-15/JB_V1_3_댓글사진_작성자권한_추가.sql`
- DEV SQL: `development/2026-11-15/JB_V1_3_보고댓글_정확한_댓글ID_반환.sql`
- DEV migrations: `jb_v13_comment_photo_author_isolation_20261115`, `jb_v13_comment_photo_filename_regex_guard_20261115`, `jb_v13_report_comment_exact_id_20261115`.
- 사진 저장 경로: `{taskId}/comments/{commentId}/{fileUuid}.jpg`. 서버가 댓글 작성자 본인이고 같은 업무에 속한 사진인지 확인한다.
- 상급자·대표님 보고 댓글은 본문 재조회 대신 **실제 INSERT된 댓글 ID**를 반환하도록 DEV 전용 새 RPC에서 처리. 기존 보고 알림 처리와 별도 호환성 시험 필요.
- 사진 업로드만 실패한 기존 댓글 아래에서 사진 재시도 UI 제공(댓글 중복 등록 방지).
- **JB-DEV 실제 RLS 트랜잭션 시험 성공**: 다른 부서 직원이 관리자 자신의 업무에 새 댓글 작성·사진 기록 INSERT 성공, 관리자 댓글에 직원이 임의 첨부하는 시도는 거부. 전부 롤백. 개발 HTML 스크립트 4개 문법·댓글 렌더/사진만 댓글 모의시험 통과.
- **미완료:** 갤럭시 브라우저에서 실제 `storage.objects` 파일 PUT/POST, signed URL 조회, 파일 형식·사진 5장 한도, 네트워크 실패·재시도/중복 푸시 시험.

### 4.2 화면 안내 문구 정리
- GitHub 개발 소스만 수정. 홈/인원배치/연차/회원가입/알림/보관함/초기화 등 **직원용 안내 약 42곳**을 삭제/축약.
- 개발·시험·내부 서버 진단 문구 삭제. 버튼·필수 도움말·실제 위험 경고는 유지. 일부 고급 푸시 공개키 입력은 화면에서 숨김(기존 DOM 기능은 유지).
- 최신 개발 HTML 관련 커밋: `04a0a5d6` → `ca765d20` → `6a3e63d`. 각각 GitHub에서 재조회할 것.
- 운영 `main` 화면에는 이 변경이 아직 없음.

### 4.3 연차·회원가입 기반 기능
- 입사일 기준 월/연차 자동 산정, 관리자 0.5일 단위 수동 차감(사유), 직원 휴무 승인과 연결된 확인·래퍼 기능은 이전에 **운영 DB+main**에도 반영된 기록 존재.
- 개근·출근율 자료 부족 → 연차 발생·잔여는 **잠정**. 1년 미만 1개월 개근 1일(최대 11), 일반 1년 이상 15일부터 근속 가산·25일 한도. 실제 법정 부여는 출근율·휴직·휴일·이월/소멸 검증 필요.
- 관리자 자기 휴무 자동 승인 경로는 신규 잠정 잔액 확인 래퍼를 우회할 수 있음. 연차 사용·취소 기록을 조작하지 말고 **테스트 계정으로 안전하게 확인**.
- 회원가입 연결, 승인 이메일 및 계정 삭제/해제는 실계정 인증 시나리오 테스트 필요.
- **운영 기록 초기화 버튼은 개발 HTML과 main HTML에서 disabled 확인.** DB RPC는 여전히 존재할 수 있으므로 연차 HR 장부 충돌이 해결되기 전까지 직접 실행 금지.

## 5. 개발용 다음 작업 우선순위
1. GitHub dev 최신 HEAD, DEV Netlify 배포 리스트에서 **최신 커밋 Published** 확인. 배포 성공과 실제 기능 성공은 구분.
2. JB-DEV만에서 개발 대표/관리자/직원 신규 **Auth 테스트 계정** 생성, 이메일 인증, 3개 가상 직원과 UID 연결. 개발용 별도 이메일 사용. 운영 DB와 계정 혼용 금지.
3. 갤럭시 기기 3종 역할별: 다른 직원 업무·관리자 자기 업무 → 댓글(텍스트만/사진만/텍스트+사진) → 사진 바로 아래 노출·재로그인 후 조회 시험.
4. 일반 댓글/상급자 확인 요청/대표님 직접 보고 3종에 대해 첨부 정확 ID 확인. 다른 작성자 댓글 첨부 거부, 업무 총 5장 제한, 파일 크기/포맷 및 네트워크 오류 시험.
5. 연차·휴무 승인/관리자 본인 자동 승인/권한·알림 중복/회원가입 연결/운영 초기화 버튼 비활성/기존 업무 사진 회귀 확인.
6. 시험 통과 시 **작업 ID·변경 파일·SQL 마이그레이션·검증 결과·유실 위험·롤백**을 공통 대장에 등록하고 **릴리스 후보**로 표시.
7. 개발용 채팅은 **운영 main에 적용하거나 운영 DB migration을 실행하지 않음**. 운영 반영은 명시 요청을 받고 실사용 서버 채팅에서 검토·진행.

## 6. 개발용 대화에서 지켜야 할 응답 방식
- 원인 → 수정 내용 → 완성 HTML/변경 파일 → SQL(조회용/설치용/삭제용 구분) → 실제 시험/미검증 → 예상 성공/실패 → 다음 단계로 보고.
- 화면 우선: 약 30명 Galaxy 직원 사용, 모바일 실사용, 느린 네트워크 및 사진 업로드 오류 처리.
- 전체 실행 가능 HTML을 기준으로 수정; 일부 코드 조각만으로 완료라고 주장하지 않는다.
- SQL과 데이터 수정은 **프로젝트 ID 재확인**, 기존 자료 보존, 트랜잭션/권한 검사, 되돌리기 계획이 우선.
- 앱 배포 성공, Supabase 마이그레이션 적용, 실제 사용자 기능 성공을 서로 별도로 기록.
- 비밀키·민감 직원 정보·비밀번호를 코드나 문서에 쓰지 않는다.

## 7. 채팅방 사이 전달 절차
- **개발용 채팅 → 실사용 채팅:** 공통 대장의 해당 `JB-...` 작업 행을 `릴리스 후보`로 바꾸고 변경 파일/커밋/SQL/검증/미검증을 적는다. 운영 채팅이 이 링크를 확인하고 승인된 변경만 운영에 반영.
- **실사용 채팅 → 개발용 채팅:** 운영 긴급 변경이 발생하면 공통 대장에 운영 커밋·원인·롤백·실제 배포 상태를 남긴다. 개발 채팅은 이를 확인해 `development-test`에 영향 검토 후 역반영.
- 양쪽 메시지가 직접 자동 동기화되지 않으므로 **GitHub 공통 문서의 갱신이 실제 전달 행위**다.
- 인수인계서나 대장을 수정할 때 해당 파일 최신 SHA를 확인하고 충돌 시 통합. 별도 승인 없는 운영 배포 금지.

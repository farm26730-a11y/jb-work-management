# JB 업무관리 V1.3 푸시 알림 지연·중복 점검 및 시험 수정 (2026-11-08)

## 목적과 사용자 증상
- 알림 발생 후 휴대폰 수신까지 시간차가 크다.
- 댓글 1건을 작성했는데 동일해 보이는 알림이 최대 3개 나타났다.
- 수정은 시험용 `development-test`에만 반영. **운영 DB·main·Netlify 배포 미변경**.

## 운영 Supabase에서 관찰한 사실 (읽기 전용)
- `jb_push_outbox` 댓글 관련 행: 2건, 각각 단일 `event_key`·단일 수신자, `attempts=1`.
- 댓글 2건 발송 기록: 작성 후 약 **22.2초** / **346.9초**.
- 346.9초 걸린 이벤트의 수신자 푸시 구독 `created_at`은 이벤트 생성 약 5분 후. 새 기기 등록 후 과거 푸시 수신이라는 설명과 일치하며, 이것만으로 Netlify 스케줄러의 5분 지연을 증명하지 않음.
- 운영 DB에 등록된 푸시 구독 총 4개 / 직원 3명. 한 직원은 2개의 서로 다른 endpoint를 보유. 동일 휴대폰의 브라우저 2개인지 실제 다른 휴대폰인지 확정 불가.
- 07:34 UTC에 task/comment/report 타입이 같은 시각에 3건 생성됐으나 수신자는 총 2명; 댓글 INSERT 트리거는 1개. 사용자에게 도착한 '같은 알림 3개'의 개별 출처는 기기/Netlify 로그로 추가 확인 필요.
- Netlify 원래 예약 주기 `* * * * *` (매분 1회). Cron 표현식으로 10초 등 초 단위 예약 간격 불가.

## 원인과 시험용 보완
1. **발송 속도:** 기존 예약 1분 주기 유지(안전망). 신규 댓글·신규 업무가 서버에 성공적으로 저장된 직후 앱이 `push-now.mjs`를 비동기로 호출해 즉시 발송 시도.
2. **엔드포인트 보호:** `push-now.mjs`는 인증된 실제 Supabase 세션, 활성 직원 연동, 해당 댓글/업무의 작성자 일치를 서버에서 확인. 2분 이내 신규 이벤트만, IP 기반 호출 수 제한. 서버의 service role/VAPID 비밀키는 클라이언트에 전달하지 않음.
3. **중복 발송:** `netlify/lib/push-core.mjs`에서 예약·즉시 발송이 같은 `jb_push_outbox` 행을 동시에 가져가려 해도 조건부 claim/처리 마커로 첫 발송만 허용. 기존 부분 성공 후 재발송을 억제하는 sent_at 정책 유지.
4. **오래된 알림:** 이벤트 생성 당시에 등록되어 있던 기기만 수신 대상으로 하고, 이벤트로부터 30분이 지난 푸시는 발송 제외. 신규 기기 등록 시 몇 분 전 알림이 몰려 오지 않도록 개선.
5. **기기 중복 표시:** `sw.js`에서 이벤트별 고유 태그 기준으로 이미 표시된 알림이나 최근 6시간 안에 본 이벤트를 재표시하지 않도록 기기 CacheStorage 기반 기록 사용. 새 SW 설치 시 빠르게 활성화.
6. **기기 다중 구독:** 동일 직원의 복수 `endpoint`는 다른 휴대폰일 수 있어 임의 삭제/합치기 하지 않음. 브라우저별 알림을 기기 전체 차원에서 병합하는 것은 불가능하므로 별도 정리 필요할 수 있음.

## 변경 파일 (모두 전체 파일 형태)
- `.../index.html` — 댓글·업무 등록 후 빠른 발송 요청
- `.../sw.js` — 동일 이벤트 중복 표시 방지 + 업데이트 활성화
- `.../netlify/functions/push-dispatch.mjs` — 기존 예약 발송을 공용 엔진에 연결
- `.../netlify/functions/push-now.mjs` — 인증 검증한 즉시 발송
- `.../netlify/lib/push-core.mjs` — 송신 공통 로직

## 정적·모의 테스트
- 전체 HTML의 JavaScript 스크립트 블록 4개 문법 검사 통과.
- 서버 3개 모듈의 파서 검사 통과 (배포된 Netlify 함수 실행 검증 아님).
- 모의 서버 테스트: 동시 발송 요청 2회에 한 번만 발송하고, outbox attempts=1 / sent_at 기록, 신규 구독 기기는 과거 이벤트 미전송.
- API 인증 모의 테스트: 유효한 사용자 작성 이벤트는 204, 잘못된 토큰은 401, 다른 작성자의 이벤트는 403, 잘못된 ID는 400.
- Service Worker 모의 테스트: 동일 tag 두 번 + 다른 tag 한 번 입력 → 총 2회 표시.
- 앱의 기존 Supabase/RLS/업무/휴무/식사 RPC 변경 없음.

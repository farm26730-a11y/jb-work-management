# JB 업무관리 V1.3 — 1단계 운영 보안·권한 점검 보고서

- 점검일: 2026-11-08 (KST)
- 대상: 운영 Supabase `bnonnvgtbukztfhaxgrr`, GitHub `main` / `development-test`
- 범위: RLS, SECURITY DEFINER 뷰/함수, 업무 수정, 근태·휴무 및 푸시 수신 대상
- 방식: **운영 DB 읽기 전용 SQL** 및 Supabase Security Advisors. **운영 DB·앱 코드 변경 없음**.
- 앱 버전 표기: V1.3 유지. 시험/변경 사항은 실제 직원 계정으로 재검증 필요.

## 발견 사항 (검증됨)

### S1 / 높음 — 휴무 변경·취소 알림 수신 대상 과다
- 함수: `public.jb_push_leave_change_event_trigger()`
- 직원 변경 신청 INSERT 시 활성 관리자 전원을 선택함: `(v_role='staff' AND app_role='manager')` 조건에 신청 직원과 동일한 `department_id` 검사 없음.
- 운영 실데이터: `leavechange:new:...` 이벤트 **3개가 각각 3명 수신자**에게 기록됨 (총 9개 outbox 행). 현재 활성 관리자는 3명 / 소속 부서 2개.
- 의도한 운영 규칙: 직원 휴무/변경 신청은 관련 부서 관리자만 처리; 대표는 통상 직원 신청 승인 대상이 아님.
- 수정 방향: 신청 직원의 부서 ID와 대상 관리자의 부서 ID를 비교. *기존 이벤트 일괄 삭제·재발송 금지*. 신규 이벤트부터 반영.
- 주의: 관리자 본인 휴무 자동 승인 경로 및 변경/취소 업무 규칙을 별도 확인하고 유지.

### S2 / 높음 — 일반 업무 보고 푸시 수신 대상 과다
- 함수: `public.jb_submit_report_core_v14(uuid,text,boolean)`
- `p_target_owner=false`일 때 `app_role='manager'` 전체에게 outbox 기록 생성. 보내는 직원의 소속 관리자 한정 조건이 없음.
- 운영 기록에서 `report:...` 이벤트 중 수신자 3명으로 기록된 사례 1건 관측.
- 수정 방향: 직원 보고는 소속 부서 관리자에게만, 대표 직접 보고는 대표에게만. 관리자 보고 라우팅은 별도 규칙 검증 후 수정.
- 주의: 기존 미확인 보고 재사용 및 고유 event_key 중복 방지 기능을 유지할 것.

### S3 / 높음 검토 — 근태 유효 상태 VIEW의 RLS 우회
- `public.jb_attendance_effective`는 소유자가 postgres이고 `security_invoker` 옵션 없음. `authenticated` SELECT 권한이 있음.
- 뷰 정의에서 `jb_attendance` + `jb_leave_requests` 조인/서브쿼리. `jb_leave_requests` RLS는 일반 직원 본인 및 관리자 부서 단위 SELECT 제한.
- 단순 `security_invoker=true` 전환 시 **다른 직원 승인 휴무가 조회되지 않아** 전사 출근/휴무가 잘못 표시될 우려. 권한 검증·유효 근태 표기 검증 없이 자동 수정 금지.
- 제안: 접근 가능한 열과 민감정보 여부를 확인하고, 필요 시 최소 권한 RPC/뷰 별도 설계.

### S4 / 중간 — 비로그인 SECURITY DEFINER 함수 실행 권한
- 비로그인 `anon`이 EXECUTE 권한을 가진 함수 4개:
  `jb_is_active_manager()`, `jb_push_leave_change_event_trigger()`, `jb_push_leave_event_trigger()`, `jb_push_task_insert_trigger()`.
- 트리거 함수는 일반 RPC 호출로 직접 데이터를 변경하기 어렵지만 불필요한 권한은 회수 검토.
- `jb_is_active_manager`는 auth.uid() 기준 검사라 익명 요청 시 보통 false이지만, 익명 EXECUTE는 불필요.
- 권한 조정 시 내부 RLS/기존 트리거 호출이 유지되는지 실제 계정 테스트 필요.

### S5 / 규칙 확인 — 전사 업무 수정 범위
- `public.jb_update_task_details` 내 `OR v_me.app_role='manager'` 조건으로 활성 관리자라면 임의의 업무 제목/설명/기한을 수정할 수 있음.
- 관리자의 타 부서 업무 지시 기능이 요구된 상황이므로 무조건 취약점으로 단정 불가. '모든 업무 수정'까지 허용할지 운영 규칙 결정 후 제한.
- 직원의 자기 업무 수정도 허용됨.

### S6 / 운영 규칙 변화 확인 — 근태 일괄 저장
- `jb_save_attendance_batch`가 현재 `owner,manager,staff` 모두 허용. 직원 인원배치 허용 요청이 반영된 코드로 보임.
- 최대 500개, 날짜별 advisory lock, 승인 휴무와 충돌 방지 검사 있음.
- 이 함수를 관리자로만 제한하면 기존 직원 근태 기능이 깨질 수 있으므로 임의 변경 금지.

## 현재 실제 데이터/배포 상태
- `main`: 운영 기준 전체 HTML (본 점검에서 변경 안 함)
- `development-test`: 신규 업무·댓글 확인, 아이콘, 식사관리 수정 포함
- DB 신규 확인 테이블은 설치됨. 2026-11-08 조회 당시 `jb_task_assignment_ack_v13` 0건, `jb_task_comment_attention_v13` 0건 (새 업무/댓글 테스트 필요).
- 운영 푸시 outbox 미발송 20건 (재시도 가능 16건, 시도 한도 4건) — 알림 작업은 2단계.
- RLS 비활성인 public `jb_*` 기본 테이블은 조회상 0개.
- Supabase Security Advisor: SECURITY DEFINER View 1건 ERROR, 익명 실행 함수 4건 WARNING. 기타 인증 실행 함수 권고는 일괄 회수 금지(앱 RPC 실제 사용).

## 적용 원칙
1. 운영 DB의 직원·업무·근태·푸시 데이터 변경 없이 수정안을 먼저 시험 환경에 적용.
2. 현재 JB-DEV는 public 업무 테이블이 없는 별도 DB이므로 실테스트를 하려면 **데이터 없는 스키마 및 최소 더미 사용자**가 필요.
3. 시험 환경에서 권한별 로그인 테스트 및 관리자·직원 시나리오 검증 후, 승인된 수정만 운영 반영.
4. 배포 시 `main`과 Netlify 배포를 구분해 기록. 미검증 코드를 정식 배포하지 않기.

# JB 업무관리 V1.3 — 업무 보고 푸시 알림 즉시 발송 시험 수정

## 요청
보고 등록 시 알림을 댓글처럼 빠르게 보냅니다.

## 원인
기존 운영 및 시험 코드에서 보고 요청은 Supabase `jb_task_report_requests` INSERT / `jb_submit_report_core_v14` RPC를 통해 `jb_push_outbox`에 `report` 타입으로 기록됩니다. 그러나 기존 빠른 전송 요청 `push-now`는 `task`, `comment`만 지원했습니다. 예약 발송은 매분 1회입니다.

## 이번 변경
- `index.html`: 새 업무 등록 후 보고, 업무 내용 수정 후 보고, 댓글에서 상급자 확인 요청 또는 대표님 직접 보고 시 서버 RPC 성공 후 `jbWakeServerPush('report', taskId)` 비동기 호출
- `netlify/functions/push-now.mjs`: `report` 허용 및 Bearer 세션으로 인증된 활성 직원의 해당 업무 보고인지 확인. 실제 보고 요청과 2분 이내 본인 작성 댓글의 내용 일치 여부를 검증
- 기존 보고의 첫 신청 이벤트 키 `report:requestId`, 미확인 요청에 대한 재보고 이벤트 키 `report:comment:commentId` 두 방식 지원
- 수신자는 DB 큐에서만 결정; 클라이언트는 업무 ID만 전달
- 공용 `push-core.mjs` 조건부 발송 점유를 그대로 사용하여 예약/즉시 발송의 중복 방지 유지
- 즉시 발송 실패 시 1분 주기 예약 발송 계속 유지
- 기존 업무·근태·식사·사용자 역할·RLS·운영 SQL 수정 없음

## 검증 결과
- 전체 HTML 내 JavaScript 스크립트 블록 4개 문법 검사 통과
- `push-now.mjs` 및 공용 발송 모듈 자바스크립트 문법 검사 통과
- 가상 Supabase 응답을 이용한 즉시 전송 테스트: 최초 보고 / 재보고 각 1회 성공(HTTP 204)
- 가상 인증 실패(401), 미등록 요청/댓글 부재/보고 내용 불일치(403): 전송 없이 거부
- 마감시간 화면 변경이 개발 HTML에 유지된 것 확인
- 운영 `main`과 Netlify 운영 배포 변경 없음

## 2026-11-10 추가 안정성 검토

### 운영 Supabase 확인 (조회 전용)
- `jb_task_comments` INSERT 트리거 `jb_task_comment_notify_v13`는 업무 담당자에게 `comment` 큐를 기록함.
- `jb_task_report_requests` INSERT 트리거 및 보고 RPC는 보고 대상에 `report` 큐를 기록함.
- 따라서 보고 시 자동 생성되는 댓글의 수신자와 보고 수신자가 같은 직원인 경우, `comment`와 `report`가 함께 생성될 수 있음. 이는 같은 행 중복 발송 문제와는 구별해야 함.
- 보고 요청과 그에 따라 생성된 댓글의 `created_at`이 같은 DB 트랜잭션 타임스탬프인 실데이터 사례 확인.
- 운영 테이블, 트리거, 구독, 실사용 데이터는 수정하지 않음.

### 개발용 코드 확정 보완
1. `push-now.mjs` 보고 이벤트 식별: 보고 작성자/업무 ID/내용/댓글 시간으로 검사; 최초 보고 요청 `report:requestId`는 동일 트랜잭션의 댓글과 연결된 경우에만 즉시 조회. 오래된 다른 보고 요청까지 깨우지 않도록 제한. 재보고 `report:comment:commentId` 유지.
2. `index.html` 즉시 전송 HTTP 4xx/5xx 오류를 콘솔에 기록. 서버가 확정하지 못한 202 응답은 별도 정보 기록.
3. `push-now.mjs` 해당 시도에서 모든 큐가 최소 한 기기 푸시 제공업체에 수락된 경우 204, 그 외(큐 없음, 일부 실패, 다른 발송자가 선점, 구독 없음 등)는 202. **204라도 Android 화면에 표시됐다는 뜻은 아님**.
4. `push-core.mjs` 이벤트 발생 당시 등록된 구독이 0개일 때 `attempts=5`, `last_error='이벤트 당시 등록된 푸시 기기 없음 (전송 대상 없음)'`으로 종결 처리. 실제 전송되지 않았으므로 `sent_at`은 NULL 유지. 매분 같은 미수신 큐가 첫 30건을 점유하는 현상 방지.
5. 신규 보고·재보고·부적절한 본문·인증 실패·빈 큐·발송 실패의 모의 테스트와 HTML JS 4개 블록/서버 모듈 문법 검사 통과.

### 배포 전 별도 검증해야 할 위험
- **중요: 보고+댓글 서로 다른 이벤트 유형이 같은 수신자에게 전송될 수 있음.** 한 건으로 합치는 것은 DB 레코드 연계와 실제 기기 수신 확인 후 설계해야 함. 본 단계는 수신자 권한/기존 댓글 알림을 임의로 제거하지 않음.
- Netlify 스케줄 함수는 분 단위 cron이며, 실제 예약 실행은 배포된 사이트에서만 확인 가능. `push-now` 엔드포인트도 아직 운영 미배포.
- 한 직원의 복수 푸시 endpoint는 서로 다른 기기/브라우저일 수 있어 임의 삭제 금지.
- `main`과 `development-test`가 서로 다른 커밋에서 분기되어 있어 전체 덮어쓰기나 무검증 일괄 병합 금지.
- `package.json`에 `^2.57.0`, `^3.6.7` 버전 범위가 쓰여 있고 잠금 파일이 확인되지 않음. 운영 반영 전 의존성 버전 고정과 빌드 확인이 필요함.
- `push-core`의 단말 구독 없음 종결 정책은 시험 브랜치에서만 검증. 새 구독으로 과거 알림을 뒤늦게 보내지 않는 현재 정책과 함께 실제 시험 필요.
- 첫 보고, 재보고, 보고+댓글 겹치는 수신자, 본인 제외, 다중 기기, 화면 꺼짐, 로그인 전환, 4xx/5xx, 작업 복구, 수신 시간 측정 등을 실제 갤럭시에서 확인해야 함.

### 결과 범위
현재 개발 브랜치에만 수정 저장. 문법/모의시험은 통과했으나 Netlify 실배포 및 갤럭시 종단 간 알림 시험을 완료한 것으로 볼 수 없음. SQL 추가 없음. V1.3 유지.

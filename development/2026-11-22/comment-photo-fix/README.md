## 확인한 원인과 조치

JB-DEV의 댓글 사진 정책은 저장 경로의 첫 번째 조각과 세 번째 조각을 기록의 업무 ID 및 댓글 ID와 대조하고, 활성 직원·댓글 작성자·업로더를 확인한다. 이전 코드는 댓글에도 일반 사진의 두 조각 경로를 썼다. 올바른 경로는 `업무ID/comments/댓글ID/사진ID.확장자`이며, 확장자는 정책과 버킷이 허용하는 JPG·PNG·WEBP다. 일반 업무 사진은 기존 `업무ID/사진ID.확장자`를 쓴다.

- 두 종류의 사진이 공통 업로더와 서버 개수 조회를 사용한다. 같은 화면·업무의 동시 실행은 차단한다.
- 기존 댓글 아래 사진 추가 입력과 등록 이벤트를 연결했다. 댓글 작성자만 추가할 수 있다. 사진 삭제 버튼은 업로더와 대표에게 표시되고 DB RPC와 Storage의 별도 권한 검사를 거친다. 완료 보관함의 사진은 조회용이다.
- 일부 업로드 실패 시 성공 수와 확인할 파일명을 표시한다. 기록 저장이 명시적으로 거부되면 해당 파일 정리를 시도하고, 결과가 불확실하면 파일을 보존한다. 댓글 저장 성공 후에는 기존 댓글의 사진 추가로 누락 파일만 선택할 수 있다. 댓글 저장 실패·응답 유실 시 기존 입력과 파일이 유지된다.
- 등록·조회 화면은 댓글 ID로 사진을 구분한다. 사진 삭제는 기존 DB RPC → Storage 제거 순서를 유지하며, Storage가 삭제 성공을 확인해 주지 않으면 경고한다.

## Supabase 읽기 전용 비교와 승인 대상

- 양쪽의 사진 테이블은 업무 ID, nullable 댓글 ID, 경로, 업로더를 가지며 경로는 고유하다. 비공개 `jb-task-images` 버킷은 5MiB 및 JPG/PNG/WEBP를 허용한다. 두 환경 모두 이 테이블에 5장 제한을 강제하는 사용자 트리거가 없다.
- 개발에만 댓글 작성자 전용 사진 업로드·기록 정책 및 정확한 보고 댓글 ID RPC가 있다. 현재 JB-DEV의 RPC는 invoker이며 로그인 역할은 내부 보고 코어 EXECUTE 권한이 없다. 기존 권한을 넓히지 않는 [개발 RPC 설치 제안](jb-dev-report-rpc-proposal.sql)을 준비했다. 적용 전 기존 함수 정의와 ACL을 보관하고, 문제 발생 시 그 정의와 ACL을 복구한다. 경로 오류의 수정 자체에는 개발 RLS 변경이 필요 없다.
- 운영에서 사진 포함 보고를 쓰려면 [기존 운영 RPC 설치 SQL](../report-comment-id-install.sql)이 별도 승인 대상이다. 타인 업무 댓글 사진도 지원하려면 개발과 동일한 범위의 작성자·업무·댓글·경로 검사를 운영에 이식하는 별도 정책 검증이 필요하다.
- 동시 접속 간 5장 보장이 필요하면 DB에서 업무별로 잠금을 잡고 INSERT 직전 전체 사진을 다시 세는 트리거를 별도로 검토한다. 현재 브라우저 잠금은 여러 탭·기기에 적용되지 않는다. 댓글 삭제의 기존 FK는 사진의 댓글 ID를 NULL로 바꾸므로 사진이 일반 영역으로 옮겨질 수 있다. 업무·댓글 삭제에 따른 파일 정리 정책을 바꾸려면 별도 범위와 승인이 필요하다.
- 개발 계정 집계는 1명이었으나 승인된 테스트 로그인을 확보하지 못했다. 개발 DB 쓰기 및 Storage 파일 생성·삭제에 대한 사전 승인도 없었다. 따라서 실서비스의 댓글 작성 → 업로드 → 목록 조회 → 삭제는 실행하지 않았다. 운영·개발 DB에서는 카탈로그 조회만 실행했다.

## 실행 HTML

[JB-DEV 전용 HTML](jb-dev-preview.html)을 내려받아 브라우저에서 연다. JB-DEV Publishable Key와 개발 테스트 계정을 사용한다. 모의 인증으로 운영 설정 무시, JB-DEV 고정, 운영 도메인 요청 차단 및 로그인 화면 진입을 확인했다. 현재 호환 보고 RPC 설치가 승인되기 전에는 실제 사진 포함 보고가 실패할 수 있다. 운영 main과 Netlify 설정에는 변경이 없다.
